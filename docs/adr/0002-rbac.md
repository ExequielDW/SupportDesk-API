# ADR 0002 — Autorización RBAC con roles

**Estado:** aceptado · **Fecha:** 2026-10-20

## Contexto
La API solo tenía un concepto de permiso: "sos el dueño del ticket". En un
sistema de mesa de ayuda hace falta que un **soporte** atienda tickets de
cualquier usuario y que un **admin** gestione cuentas y roles.

## Decisión
Tres roles con jerarquía: `usuario` (0) < `soporte` (1) < `admin` (2).
- El rol y el flag `disabled` **los asigna el servidor**; nunca se aceptan desde
  el cuerpo de la petición.
- Dependencias de FastAPI: `current_user`, `require_soporte`, `require_admin`.
- Anti-escalación: solo `admin` asigna roles; solo `admin` degrada a otro `admin`;
  el **último admin no se puede degradar ni deshabilitar** (409).
- Los endpoints existentes siguen aislados por propietario (anti-IDOR).

## Alternativas consideradas
- **Solo propietario**: más simple, pero no modela el flujo real de un agente.
- **Permisos granulares por endpoint**: más flexible, complejidad innecesaria
  para tres roles.

## Consecuencias
- `User` expone el rol; `UserCreate` ya no acepta `disabled` ni `rol`.
- Los tickets de otros usuarios se listan en `GET /tickets` (solo staff).
- Cambiar el estado de un ticket se valida contra transiciones permitidas.
